# PHP Runtime Audit

A local-first PHP runtime security audit and patch-verification project. The initial focus is PHP2Shell; the product is intended to support versioned PHP advisories over time.

> **Status:** Early local CLI version. It gathers Linux PHP runtime evidence and evaluates a versioned PHP2Shell advisory pack. Unknown results are expected when the running SAPI, package provenance, or configuration cannot be established.

## Bootstrap the governed development workflow

The audit tool runs on PHP 8.2 or newer (the governed development toolchain requires PHP 8.3+ and Composer). It can inspect target hosts with PHP 5.x, 7.x, and 8.x installations, including side-by-side CLI and web runtimes. Discovering a legacy target does not mean the audit tool itself runs on that legacy PHP version, and the audit tool's PHP version does not establish target patch status.

## Product intent

- Audit local PHP runtimes, SAPI/process identity, distro backports, extensions and relevant configuration.
- Distinguish **patched**, **potentially affected**, **unverified** and **investigation required** from independently observed indicators of compromise.
- Generate read-only, locally executable checks, machine-readable evidence, and proposed remediation for a human or coding agent to review.
- No URL-driven active exploitation, no intrusive production tests, no upload of private server data by default.

See [the implementation plan](docs/IMPLEMENTATION_PLAN.md) for deliverables and gates.

## Run a local Linux inventory

Install production dependencies and run the local inventory command as the account that can read the system's process and package information:

```bash
composer install --no-dev --no-interaction --prefer-dist
php bin/php-runtime-audit-inventory > runtime-report.json
```

The command prints a versioned JSON report to standard output. It makes no network requests and does not change packages or services. It uses fixed local commands, bounded output and timeouts. Subprocesses require an observed loopback-only network namespace with restricted capabilities and no-new-privileges, or a fixed namespace-isolation wrapper. If isolation is unavailable, those probes fail closed and their facts remain unknown; ordinary host execution may therefore produce an incomplete report. It does not accept domain names, run exploit payloads, or export evidence to a hosted service. For development and CI, `--fixture <directory>` reads an offline fixture and never starts a subprocess.

Each report includes the OS identity, separate CLI and web-worker versions, package-manager evidence, Apache module mappings, SAPI-scoped PHP settings where their configuration paths are known, configured extension directives, worker start ticks, source digests and advisory citations. CLI-only settings are not used as FPM or Apache evidence. A setting with missing, conflicting, symlinked or truncated source data remains unknown. A suspicious value in any inspected applicable web-SAPI configuration source may request investigation, but does not change patch status or prove that a worker loaded the setting. Worker version evidence is withheld if a versioned process name, executable and before/after `/proc` identity do not agree, or an explicit argv version conflicts. The CLI probe runs PHP with `-n`; it records compiled-in CLI extensions while configuration files record extension directives separately. It does not load the host's configured extensions during collection.

Patch results use four verdicts: `verified_fixed`, `potentially_affected`, `unknown`, and `needs_investigation`. A fixed installed package cannot prove that a running worker loaded the same code. Unsupported or conflicting vendor evidence remains `unknown`. An exact fixed installed-package version is insufficient for a running-worker green verdict: Debian/Ubuntu proof additionally checks the local package database and its executable integrity record against the installed and loaded executable. This trusts the local package database; it does not authenticate a compromised host. RPM/APK loaded-package integrity is not yet established, so exact package versions alone remain unknown. Remote advisory URLs are citations, not captured response bodies: their capture digest stays absent. The separately identified bundled catalog has its own content digest and as-of date. Every assessment keeps compromise evidence separate; a fixed patch result does not mean the host was never compromised.

This version covers Linux process/package inventory and PHP2Shell advisories CVE-2026-109618, CVE-2026-109619, and CVE-2026-115560. It is not a general security certification. Review the evidence and source revisions before making operational decisions.

## Generate a reviewable remediation plan

PRA-5 turns a runtime audit report into reviewable remediation proposals, as both machine-readable JSON and a human-readable `REPORT.md`:

```bash
php bin/php-runtime-audit-inventory | php bin/php-runtime-audit-report --report REPORT.md > remediation-plan.json
```

The command is a pure transformation of the report already produced by `php bin/php-runtime-audit-inventory`: it collects no new evidence, runs no commands, and never restarts, installs, or modifies anything. Every proposal requires explicit human approval and states its own prerequisites, risk, rollback and verification steps; `requires_human_approval` is always `true` and cannot be set otherwise. A `verified_fixed` verdict that cites no evidence present in the report is flagged rather than reported as a clean result, and conflicting assessments for the same subject are both kept visible rather than merged. The input is treated as untrusted: malformed or unresolvable records are skipped and recorded as warnings instead of producing a guessed proposal, and all generated text is bounded and stripped of control characters before it reaches the Markdown report.

## Validate local evidence records

PRA-3 adds versioned evidence records for observations, applicability, assessments, coverage and findings. The validator checks one caller-supplied local JSON file against the bundled v1 schema, applies typed-model consistency checks, and writes a structured result to standard output:

```bash
php bin/php-runtime-audit-evidence validate tests/fixtures/evidence/v1/observation.valid.json
```

The command accepts only a local file path, rejects URL and UNC paths, reads at most 1 MiB, rejects duplicate JSON object keys, and does not resolve source locators contained in the record. Source freshness is derived only from the captured and current SHA-256 digests already present in the JSON. Missing digest evidence remains `unknown`. An assessment keeps patch status separate from compromise evidence. `verified_fixed` and `potentially_affected` patch statuses require evidence IDs; `none_observed` means no compromise was observed in the supplied evidence and does not mean the host was never compromised.

Schema version `1.0` is stored under `resources/schemas/evidence/v1/`. Unknown record types and schema versions fail closed. The validator does not collect runtime facts, decide vendor backports, or establish whether a host is safe.

## Security

Never treat `php -v`, response headers or HTTP success as proof of a patched web-facing runtime. No shell pipelines from remote user input. Treat generated instructions and collected logs as untrusted data. Never store SSH credentials in the website.

## Delivery milestones

The Local MVP requires independently verified runtime/patch evidence and reviewable remediation instructions. The Public MVP adds documentation and reproducible security-reviewed download bundles. Source analysis and incident forensics are separate follow-up slices. See the implementation plan for current gates; this checkout does not claim a completed public release.
